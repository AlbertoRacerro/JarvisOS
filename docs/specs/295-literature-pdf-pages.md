# 295 — LITERATURE-PDF-PAGES-1: Check a literature number on its PDF page

Status: ready
Depends on: 294

## Goal

A datum recorded from a PDF source with a page locator is checked like a text datum: the number must appear in the text
layer of the stated pages. The Literature page offers "Pages from/to" for PDF sources whose text could be read, and says
plainly when a PDF has no readable text (for example a scan).

## Why

Most acceptance-case papers are PDFs. After spec 294 a PDF can be attached, but every datum on it reads "Not checked".
Contract [248](248-design-value-path.md) slice F names Docling for extraction into values, including tables; that needs a
large install and is a later slice. Locating a number on a page needs only the PDF text layer. `pypdfium2` (5.x,
BSD-3-Clause/Apache-2.0, binary wheels, no model download) reads it, and Docling itself uses it as its PDF backend, so
adding it now does not duplicate the later Docling slice.

## Scope

In scope:
- Add `pypdfium2` pinned in `backend/requirements.txt`. Record name, version and licence in the PR.
- `backend/app/modules/memory/pdf_text.py`: `read_pdf_pages(path) -> list[str]` returns the text layer of each page in
  order, with `pypdfium2`. It is bounded: at most 2,000 pages and 2,000,000 characters in total, otherwise
  `PdfTextError`. An encrypted or unreadable PDF raises `PdfTextError`. It never runs OCR and never touches the network.
- A derived page-text cache beside the upload, `<sha256>.pages.json` (`{"extractor": "pypdfium2", "extractor_version":
  ..., "pages": [...]}`). It is written atomically on first need and reused while the extractor version matches. A PDF
  whose pages are all empty after whitespace stripping is recorded with `"pages": []` and the state `no_text`.
- `LiteratureBackingRead` gains `page_text: "available" | "no_text" | "unreadable" | None` (`None` for non-PDF
  backings).
- Checks: for a PDF backing, a `page` locator selects pages `locator_start..locator_end` and runs the same number or
  literal-text match as spec 293. The check is `fail` when the range is outside the page count, and `not_evaluated` with
  a hint naming the state when the text is `no_text` or `unreadable`. Line locators on a PDF stay `not_evaluated`.
- `_validate_locator` accepts a `page` locator on a PDF backing whose page text is available and whose range is within
  the page count; every other case keeps today's refusal.
- Frontend: for a PDF backing with `page_text == "available"`, the datum form shows "Pages from/to" instead of "Lines".
  For `no_text` it shows "This PDF has no readable text (it may be a scan); values on it cannot be checked yet." Update
  `frontend/tests/114-literature-knowledge.mjs`.
- Extend `e2e/literature_datum_walk.mjs`: attach a small text PDF that the walk generates, record a datum on page 1, and
  see "Checked against the source"; a wrong page reads "Does not match the source". The test PDF is generated by the
  walk or test with `pypdfium2` or as literal minimal PDF bytes; no binary fixture is committed.

Out of scope (binding non-goals):
- Docling, OCR, table extraction, model-proposed values, or any network access.
- Schema changes; the cache is a derived file and is rebuildable.
- Changing text or markdown behaviour from specs 293 and 294.

## Design constraints

- The cache path is derived only from the stored artifact path (same directory, same sha256 stem); it is never built
  from client input. Writes go to a temporary file in the same directory and are then renamed. Symlinked cache files are
  ignored and rebuilt.
- Extraction runs at most once per sha256 and extractor version. Reading a source with N PDF datums reads the cache
  once.
- A failing or missing `pypdfium2` import makes PDF checks `not_evaluated` with a clear hint and never breaks the read
  routes.
- Tests are offline and build their PDFs in the test; no binary fixtures.

## Acceptance criteria

1. A generated two-page PDF whose page 2 contains `k = 1.2 x 10^-3 s^-1`: a datum `0.0012` with page locator 2–2 reads
   `usable`; with page 1 it reads `not_usable`; with page 3 it is refused at creation (out of range).
2. A PDF without a text layer reads `page_text == "no_text"`, and a page-located datum on it is refused at creation. A
   datum without a locator reads `unchecked`.
3. The cache file is written once; a second read does not call `read_pdf_pages` (asserted with a counting stub).
4. A corrupt PDF (valid `%PDF-` header, broken body) reads `page_text == "unreadable"` and the source still loads.
5. The extended walk passes from a clean profile, and its evidence is attached to the PR.
6. ruff, focused backend tests, `npm run build`, contracts check, architecture enforcement and the typecheck ratchet
   pass.
